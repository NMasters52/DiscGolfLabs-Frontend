### [x] 1. Make the access sheet use only its own course check

The open sheet watches every course check. A slow check for another card can make this sheet show an error or disable Retry.

- Where: `app/routes/app/courses/index.tsx` and `app/components/courses/CoursesView.tsx`
- Fix: Find the check for the open sheet's `courseId`. Use only that check for loading, errors, and Retry.
- Source: [issue #63](https://github.com/NMasters52/DiscGolfLabs-Frontend/issues/63)

#### Findings

The issue was caused by two page-level decisions in `app/routes/app/courses/index.tsx`: Retry refetched every enrollment query, and `isSheetRetrying` became true when any enrollment query was fetching. Because enrollment checks are stale after five minutes and TanStack Query refetches stale data when the tab regains focus, an unrelated or background refetch moved a healthy sheet into its error presentation. The sheet's own query is now resolved by `courseId`; Retry and the fetching flag use only that query. An in-flight check has a separate `checking` presentation, so it does not look like a failed check.

### [x] 2. Stop the access sheet from closing and reopening by itself

A course-list refresh can remove an open sheet. When the list recovers, the sheet can reopen without a click.

- Where: `app/components/courses/CoursesView.tsx` and `app/routes/app/courses/index.tsx`
- Fix: Clear `sheetCourseId` when the page is no longer ready. Keep old cards visible during a failed background refresh if possible.
- Source: [issue #64](https://github.com/NMasters52/DiscGolfLabs-Frontend/issues/64)

#### Findings

`CoursesView` returns early for loading, loadError, and empty states before the sheet renders, so a background failure of the course list unmounted an open sheet without a controlled close — focus fell to the body and `onCloseAutoFocus` never fired — while `sheetCourseId` survived in route state, letting the sheet pop open again once the list recovered.

The fix works from both ends. First, the view model keeps cached cards usable: `createCoursesViewModel` only enters loadError when there is no course data at all, so a failed background refresh keeps the last successful list (which TanStack Query retains) rendering instead of tearing the page down. Second, the route now reconciles `sheetCourseId` against the rendered view model through `reconcileSheetCourseId`: the selection survives only while the page is ready and the course still has a visible card. If a refresh drops the page out of ready or removes the course from the list, the selection clears — so recovery can never reopen the sheet without a click.

One incidental fix: reformatting the test file's import across multiple lines broke the `@ts-expect-error` pairing with the `.ts` extension, which surfaced two new typecheck diagnostics; the directive now sits on the line carrying the import path, and the changed files are clean.

### [x] 3. Clear old enrollment data after checkout or account changes

Enrollment data stays fresh for five minutes. A buyer can still look unenrolled, and a new user on the same device can briefly see the last user's course state.

- Where: `app/queries/useEnrollments.ts` and `app/root.tsx`
- Fix: Clear cached queries when the Clerk user changes. Refresh enrollment checks when a user returns from checkout.
- Source: [issue #66](https://github.com/NMasters52/DiscGolfLabs-Frontend/issues/66)

#### Findings

Two causes. First, the checkout success page polls `fetchEnrollment` directly, outside TanStack Query, and navigates the moment it sees `enrolled: true` — so the authoritative answer existed but never reached the shared check key, which still held the pre-checkout `enrolled: false` for up to five minutes across the learn gate, course home, and index cards. Second, the `QueryClient` is a module-level singleton in `app/root.tsx` and nothing cleared it when the signed-in Clerk user changed, so the next user on the device read the last user's enrollment and progress from cache.

The account-switch half is a new `AuthCacheReset` component (`app/components/app/AuthCacheReset.tsx`), rendered inside both providers in `root.tsx`: it watches `useAuth().userId` and calls `queryClient.clear()` on every resolved user transition — sign-out, sign-in, account switch. The decision is a pure helper, `shouldClearAuthCache` (`app/queries/auth-cache.ts`), because Clerk's initial `undefined -> userId` resolution is app load, not a user change, and must keep the cache. The checkout half seeds the shared check key with the polled answer (`queryClient.setQueryData`) right before the success page navigates, so every consumer renders the new enrollment immediately; the five-minute `staleTime` is untouched elsewhere and keeps absorbing repeated reads.

### [x] 4. Show a real not-found page for a bad course link

A bad course slug shows a Retry button that can never work because a 404 is treated like a server failure.

- Where: `app/api/course.js` and `app/routes/app/courses/$slug.tsx`
- Fix: Keep the HTTP status. Show a not-found message and a link back to `/app/courses` for a 404.
- Source: [issue #65](https://github.com/NMasters52/DiscGolfLabs-Frontend/issues/65)

#### Findings

`fetchCourse` flattened every non-OK response into the same opaque `Error("course not found")`, so nothing downstream could tell "this slug has no course" from "the server failed" — an unknown slug rendered the retryable load-error card, whose Retry re-hit the identical 404 forever with no way back.

The fix keeps the status the API already provided. `CourseApiError` (`app/api/course.js`) carries the HTTP status out of `fetchCourse`; the course-home view model gains a `notFound` state detected by `isCourseNotFound` (a duck-check on `status`, so the decision is unit-testable without the network layer), and a 404 wins over enrollment errors, which can only exist because the course never resolved. `CourseHomeView` renders a not-found card — deliberately no `role="alert"` and no Retry, because the API answered — whose CTA links back to `/app/courses`. Non-404 failures keep the load-error card unchanged. The route file needed no change: it already passes the query error through. This also settles `/app/courses/learn`, which matches `courses/:slug` with slug `learn` after URL pruning: it now renders the not-found card instead of the retry dead end.

### [x] 7. Match enrollment checks to cards by course ID

The page matches results to cards by list position. One course with a missing ID can put the wrong enrollment state on later cards.

- Where: `app/routes/app/courses/index.tsx` and `app/components/courses/courses-view-model.ts`
- Fix: Match results with a map keyed by `courseId`.
- Source: [issue #69](https://github.com/NMasters52/DiscGolfLabs-Frontend/issues/69)

#### Findings

The route passed the `useQueries` result array straight into `createCoursesViewModel`, which paired `enrollmentResults[index]` to `courses[index]`. The route filters blank IDs out of `courseIds` before creating checks, so a course with a missing ID shifted every later card's enrollment state onto the wrong course. The route already built a `courseId → query` map for the access sheet; that map is now built once and handed to the view model as `enrollmentByCourseId`, which looks up each card's check by its own ID. A card with no ID (no map entry) stays in its loading state instead of borrowing a neighbor's result. The view model's ID derivation (`_id ?? id`) is unchanged; the route's list keeps the typed `_id`-only shape of `CourseListItem`.

### [x] 12. Give course lists and course details different cache keys

The course list and a course with the slug `list` would share one cache key and mix their data.

- Where: `app/queries/keys.js`
- Fix: Use a detail key such as `["course", "detail", slug]`.
- Source: [issue #70](https://github.com/NMasters52/DiscGolfLabs-Frontend/issues/70)

#### Findings

`course.bySlug(slug)` produced `["course", slug]`, so a course with the slug `list` collided with `course.list()` at `["course", "list"]` — the index and that course's detail page would read and overwrite one cache entry. The key is now `["course", "detail", slug]`. Only two call sites consume the course keys (`useCourses.ts`, `useCourse.js`), both through the factory, and nothing invalidates the `["course", …]` prefix, so no other code needed to move. Enrollment, game-session, and stats keys are untouched.
